# Quran Landing Page — Project Plan

## Goal
A $10,000-quality landing page for a Quran website — a pure visual "hook," not the full site. Everything beyond the landing page is out of scope until this phase is locked and built.

## Why this approach (history)
- **Attempt 1:** Full site research (page/media structure), hardcoded directly in Opus. Effort got diluted across too much scope at once — came out wrong.
- **Attempt 2:** Landing-page-only, user-supplied Quran images. Turned into one crammed single-page app with no real design system behind it — looked cheap, not "like a Claude website."
- **Attempt 3 (this plan):** Claude plans phase-by-phase here first. Each phase is locked before the next starts. User pastes each locked phase into Opus ("ultracode" = Claude run at max effort, not a separate tool) to hardcode.

## Stack
Plain HTML/CSS/JS. No build tools, no framework — so each phase can be pasted in and seen working immediately.

## Hero concept
Scroll-scrubbed animation: as the user scrolls, the Quran visually opens (cover lifts / pages part) — Apple product-page style, scroll position drives playback, not autoplay.
- Static hero image generated by AI first (this phase).
- Video/animation frames generated in a later phase — **hold off on video prompts until user confirms that phase has started.**
- User has Google Pro (Imagen/Veo via Gemini) — generation prompts should target that toolset.

## Hard constraint: AI + Arabic text
AI image/video generators reliably mangle Arabic script. Any visual needing legible Quranic verse text must use real photography/calligraphy instead. AI generation is fine for the Quran object itself and for atmospheric elements (light, dust, geometric motion, texture) as long as no readable verse text is required in the render.

## Design direction
Elegant, simple, built for a lasting/memorable impression — not maximalist or feature-crowded. Must support **both light and dark mode properly** (dark is not just an inverted light mode).

Full palette, typography, spacing, motion spec, and pre-delivery checklist: [design-system/quran-landing/MASTER.md](design-system/quran-landing/MASTER.md) — generated + persisted via the `ui-ux-pro-max` skill (real database query, not invented), with a hand-derived dark-mode palette layered on top since the tool only returns one fixed palette per query.

- **Palette:** Primary near-black `#1C1917`, background `#FAFAF9`, gold accent `#A16207` (light) / `#D4AF37` (dark) — "Premium black + gold."
- **Typography:** Bodoni Moda (headings) + Jost (body) — luxury/minimalist/refined pairing.
- **Hero opening mechanic (RESTORED 2026-09-13):** the cover lifts from its free edge and swings on the spine. It must NOT split symmetrically from the centre.

  **This rule was reversed and then reinstated the same day.** A centre split was tried at the user's request, built, and rejected on sight: *"how can a book magically open from the center when its spine is on the right."* There is no hinge at the centre of a bound book, so the motion reads as fake no matter how cleanly it is executed. Treat this rule as settled and do not reopen it — the prototype that proved it is at `hero-prototype.html`.

- **The book must translate as it opens.** Closed, the book occupies width W. The cover pivots on the right-hand spine and swings rightward, so when open the pair spans 2W — the growth is entirely to the **right**. Left unhandled, the book slides off-centre as it opens.

  **Fix — put the spine at the exact centre of the generated frame, and do the recentring in CSS.** The generation keeps a dead-locked camera (no pan, no zoom, nothing for the model to drift); the element is then translated on scroll from `+W/2` (closed book reads centred) to `0` (open spread reads centred). This is the "move it" the user asked for, kept in code where it stays tunable instead of baked into footage.

- **Inside of the front cover = plain cream endpaper.** Never a mirrored or reversed copy of the front calligraphy, never the roundel showing through. With the inside cream, the open state reads as a proper two-page spread.
- **Hero pose (corrected 2026-09-12):** book stands upright, front cover facing the camera nearly head-on — not lying flat / not a three-quarter table-top shot. Spine is a vertical edge on the right side of frame, page edge on the left.
- **Opening direction (corrected 2026-09-12 — earlier entries had this backwards):** the cover swings **left to right**. The spine is on the right, so the *free* edge is on the left; it lifts and sweeps rightward, pivoting on the right-hand spine. This is the mirror of a Western book. Do not confuse it with Arabic *reading* direction, which is right-to-left — the text flows RTL while the physical page motion goes LTR. Conflating the two is what produced the earlier error.
- **Working order:** perfecting the dark-mode hero image alone first; light-mode variant comes after dark is locked.

### Asset principle (locked 2026-09-12) — applies to every generated image and video
Generate **clean flat assets, not finished photographs.** No baked-in tilt, perspective, directional lighting, cast shadows, vignette, glow, or particles. Straight-on orthographic front view, evenly lit corner to corner, flat solid background, tight crop.

**Why:** baked-in lighting and perspective can't be re-themed between light and dark mode, and a tilted source fights the scroll-open animation. Glow, shadows, atmospheric particles, and depth are built in CSS/canvas at implementation time — animatable, themeable, and far lighter than shipping two moody photographs. The generated asset is the book; the hero section is composed around it in code.

**Flat means flat:** no page edges visible on the left, no spine edge visible on the right, no book thickness at all — only the rectangular cover face. If either edge is visible, there is still rotation in the image.

**Cover colourway (locked):** near-black / deep espresso leather with antique gold tooling — not mid-brown. Chosen so the asset sits natively on the `#1C1917` dark ground with `#D4AF37` gold, per the design system.

**Cover design language (locked 2026-09-12, from user reference):** restrained and minimal, not densely ornate. Black field with subtle low-relief tone-on-tone texture, one thin gold double-rule border inset from the edges, single small gold roundel centred. Sparing gold. The earlier heavily-tooled arabesque direction is rejected as too busy.

**Calligraphy (revised 2026-09-12):** the centre roundel carries القرآن الكريم, generated directly in the image. This short phrase appears on a huge number of real covers and renders acceptably; the earlier blanket "never generate Arabic" rule was too strict for it. Verify the glyphs by eye before shipping — subtle malformation is the failure mode.

Longer or less common Arabic — the scrolling aayat above all — still must be live text, never generated artwork.

**Orientation — two separate things, state both every time:**
- **Canvas:** landscape 16:9 (approved black asset is 2816×1536). Never a portrait canvas.
- **Book:** portrait, roughly 2:3, centred in that landscape canvas with empty background either side, whole and uncropped.

Conflating these produced a mismatched pair once already — the white variant came back as a tight portrait crop (1846×2304).

**Asset pair (locked 2026-09-12):** dark-mode cover approved. The light-mode cover is the same asset in ivory-white with gold — identical composition, proportions, border, roundel placement and framing, colourway only. Not a horizontal flip; spine side stays consistent. The two must stay pixel-compatible so toggling theme swaps the image without shifting layout.

**Output size:** roughly 1200–1600px tall is plenty for a hero asset; convert to WebP for the build (the design system checklist requires WebP/AVIF). No need for huge multi-MB generations.
- **Aayat on scroll:** 3-4 different verses should appear/cycle as the user scrolls the hero. This text must be real type (HTML/CSS text or a proper Arabic font), never baked into the AI-generated image or video — same reason AI can't render legible Arabic script reliably. The static hero image and generated video stay text-free; verse overlays are a separate live-text layer built in Phase 5.
- The design system's suggested page "Pattern" (multi-chapter problem/journey/solution) does not fit this brief — only its motion, accessibility, and anti-pattern rules apply, not its section structure.

## Page structure (locked 2026-09-12)

The whole page, in scroll order. Nothing else gets added without a reason.

1. **Rest** — book closed, centred, quiet wordmark.
2. **Opening** — scroll swings the cover open, the free edge on the left sweeping rightward, pivoting on the right-hand spine. The book translates left as it goes so it stays centred. Nothing else happens during this; the opening is the entire event.
3. **Fully open** — the book settles open, pages visible. No text yet.
4. **Aayat** — only now do the verses appear, 3-4 of them, cycling on the open pages as scrolling continues.
5. **Close** — one short line saying what the site is, one restrained entry point.

**Deliberately excluded:** feature grids, testimonials, stat counters, newsletter signup, FAQ, link-farm footer. The user asked for "pure atmosphere"; the wordmark and closing line are the minimum needed for a visitor to know what they're looking at and how to enter. Everything beyond that is template furniture.

## Opening animation — CSS, not video (decided 2026-09-13)

**Veo is dropped for the opening.** A symmetric centre split is a geometric
transform, not paper physics — it is two `rotateY` transforms, so generating it as
video buys nothing and costs everything that went wrong in attempt 1.

Built instead from two flat stills plus CSS:

- `assets/hero/quran-dark.webp` — the closed cover, already approved
- an open-spread still (two blank cream pages) — **the one asset still to generate**

The closed cover is drawn as two halves, left and right. Scroll drives each half
outward on `rotateY`, pivoting on its **outer** edge, revealing the spread beneath.

Why this is strictly better than the video:

| Problem in attempt 1 | Under CSS |
|---|---|
| Gemini watermark | Gone — nothing is generated as video |
| Camera drift / scale growth | Impossible — there is no camera |
| Direction reversal | Impossible — scroll position *is* the rotation angle |
| Ghost / dissolve morphing | Impossible — the asset never changes |
| Mirrored calligraphy on the inside face | We define the inside face ourselves |
| ~3 MB video + frame extraction | Two images, no decode step |
| Light/dark variants | Swap the image; the transform is identical |

**Inside faces (locked 2026-09-13):** the reverse of each cover half is plain
endpaper — flat near-black, no roundel, no gold rule, no reversed script, nothing
showing through. The user called this out explicitly. In CSS this is a separate
back-face layer, not a flipped copy of the front.

### The roundel conflict

The gold roundel carrying القرآن الكريم sits dead centre, so a centre split cuts it
in half. Two ways out:

1. **Fade the roundel and gold rules out over the first ~15% of the scroll, before
   the split begins** — the cover becomes a plain black field, then parts.
   **Recommended.** Nothing sacred is ever torn.
2. Let it split cleanly as a gatefold would. Geometrically clean, but it does divide
   the calligraphy down the middle.

Going with (1) unless the user says otherwise — it is a one-line change either way.

## Opening animation — superseded Veo approach (decided 2026-09-12)

**Veo frame sequence**, generated **image-to-video** from `assets/hero/quran-dark.webp` as the starting frame — not text-to-video. This guarantees frame 1 is the approved hero asset, so there is no seam or colour mismatch between the static state and the animation.

Non-negotiables in the generation: locked-off camera, unchanged lighting, flat identical background, book centred at constant scale, **blank cream pages with no text of any kind**, cover swinging **left to right**, and constant-speed motion with no easing (easing fights scroll-scrubbing).

Frames get extracted and drawn to canvas on scroll. Real aayat are laid over the open pages as live text — never generated.

**Audio:** Veo generates sound, and produced a door-creak effect on the first attempt. Irrelevant either way — we extract frames and discard the audio track entirely. A silent-clip instruction is included in the prompt only to stop the model shaping the motion around an imagined sound.

**Sway (requested 2026-09-12):** the book should sway slightly around its vertical axis as it opens. This is built in **CSS, not Veo** — a small scroll-driven `rotateY` on the canvas element. Baking it into the video would violate the locked-off camera rule, make frames impossible to match to the static asset, and remove any ability to tune the amount. Keep the generated footage dead-on and flat; add dimensionality in code where it stays adjustable.

### Attempt 1 rejected (2026-09-13)

`videos/The_book_s_front_cover_swings.mp4` (1280×720, 10s) failed on six counts —
direction reverses at ~6.4s after a ghost/dissolve at ~5.5s, camera zooms and drifts
right, it opens past the cover to a middle spread, pages carry foxing stains, and a
Gemini sparkle watermark sits bottom-right throughout.

**Diagnosed by extracting frames, not by eye** — see `videos/grab-frames.ps1`.

**Strategy change:** pin **both** ends. Use Google Flow's *Frames to Video*
(first frame + last frame) rather than first-frame-only image-to-video, and shorten
the clip to 5–6s. A 10s unconstrained generation gives the model too much room to
drift; pinning only frame 1 is not enough to stop it. This adds a prerequisite —
an approved **end-frame still** (`quran-dark-open.webp`: same camera, same scale,
cover fully open to the right, one blank cream page), generated with Imagen under
the same flat-asset principle and normalised to the same canvas.

Full failure table, corrected prompt, negative prompt, and the delivery checklist:
[videos/veo-prompt.md](videos/veo-prompt.md).

**Tooling note:** system `ffmpeg` (`C:\ffmpeg-8.1.2-essentials_build\bin\`) is a
broken 533 KB install missing its DLLs — it exits 0 and silently does nothing.
Python is blocked from executing inside the Claude sandbox. `videos/grab-frames.ps1`
works around both with pure .NET WPF `MediaPlayer` scrubbing.

## ⚠ Something on this machine stamps .jpg files (found 2026-09-13)

**Do not save project assets as `.jpg` on this PC.** Something is rewriting JPEG
files and stamping `I am Sorry !!!!!` into the bottom-left corner.

Evidence:

- Four `.jpg` files written at ~00:36 were all silently rewritten at **00:49:08**
  with different file sizes and different hashes. Nothing in this session did that.
- Every one carried the same stamp at the same place — bbox `x 11..576, y 929..1053`
  on a 1920×1080 frame, identical across files with completely different content.
- The text is **dark**, so it is invisible on dark areas and only shows on light
  ones. It was spotted on the cream pages of `spread-dark.jpg`; it was equally
  present on `frame-first.jpg` and only found by boosting the levels 7×.
- `open-spread.jfif` and `quran-dark.webp` were **never touched**. The stamper
  appears to target `.jpg` only.

**Workaround in use:** build frames straight from the untouched sources to **PNG**,
never landing on an intermediate `.jpg`. See `C:\Temp\qf\rebuild-png.ps1`.

**Verify before every upload.** Boost the levels on the bottom-left corner and look —
a visual glance is not enough, because the stamp hides on dark ground. `corner.ps1`
flags it: a bbox starting left of x=382 (outside the book) means the file is stamped.

The user should find out what is doing this. Until then, treat any `.jpg` written to
this project as suspect.

### Animation assets (2026-09-13) — tight crops, no padding

The padded assets above are hero *display* stills. The split animation needs the
book with **no surrounding background**, or the rotating halves would carry
background-coloured rectangles with them.

| File | Size | Purpose |
|------|------|---------|
| `assets/hero/cover-dark.jpg` | 907×1349, 493 KB | Closed cover, tight crop. Split down the middle into two leaves. |
| `assets/hero/spread-dark.jpg` | 1814×1349, 167 KB | Open spread, tight crop. Each page exactly 907 = cover width. |
| `assets/hero/open-spread.jfif` | 2752×1536 | Imagen original, kept |
| `assets/hero/frame-first.jpg` | 1920×1080, 287 KB | **Start frame for generation.** Closed cover, spine on the exact centre (x=960). |
| `assets/hero/frame-last.jpg` | 1920×1080, 117 KB | **End frame for generation.** Open spread, fold on the exact centre (x=960). |

The two generation frames are **composed, not generated** — both are built from the
approved stills by `C:\Temp\qf\frames.ps1` on a 1920×1080 near-black canvas, book
height 860 at y=110, cover at x 382..960 and spread at x 382..1538. Because the
closed cover occupies exactly where the first page will be, and the spine and fold
both land on x=960, the model has no room to reposition, rescale or drift.

Rebuild them by re-running `crop.ps1` → `tojpg.ps1` → `frames.ps1`.

Measured before cropping — the spread came back genuinely clean: fold 2px off
canvas centre, pages 956/956 with **0px** difference, background flat at lum 27
across the whole field with no baked halo, pages unmarked.

The spread was 5.5% wider per page than the cover, so it was scaled non-uniformly
(0.948 × 0.984) to make each page exactly 907×1349. On blank cream paper that
differential is invisible, and it makes cover and pages align exactly.

Convert both to WebP before shipping — these are JPEGs only because nothing on this
machine can encode WebP.

Originals kept as `dark quran image.jfif` / `light quran image.jfif`.

The two generations did not match as delivered — dark book measured 906×1350, light 840×1211, on different canvases (2816 vs 2752 wide), with the light one slightly off-centre. Both were rescaled to a common 1350px book height and recentred on an identical 2816×1536 canvas, so a theme toggle swaps them with no visible jump. Regenerate-and-hope was avoided deliberately; if either asset is ever regenerated, re-run the same normalisation.

Note: the dark generation's background carries a faint gradient rather than being perfectly flat. Its base tone reads `rgb(27,27,27)` ≈ `#1B1B1B`, near-identical to the locked `#1C1917` ground, so it composites cleanly regardless.
